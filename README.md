### Дві речі, які варто знати перед стартом
- **`~`** — це твоя домашня тека. На Mac це `/Users/<твоє-імʼя>`, наприклад `/Users/bohdanhnidenko`. Тобто `~/.zshenv` = `/Users/bohdanhnidenko/.zshenv`.
- **Крапка на початку назви** (`.claude`, `.zshenv`, `.pipeline`) робить файл чи теку прихованими. У Finder їх видно, якщо натиснути `Cmd + Shift + .`. У терміналі їх показує `ls -la`.

## Частина A. Один раз на комп'ютер

### A1. Перевір, що є Node.js і git

```bash
node -v     # потрібно v18 або новіше
git --version
```

Якщо `node` не знайдено, встанови його з https://nodejs.org (версія LTS) і перезапусти термінал.

### A2. Скачай кіт

```bash
mkdir -p ~/dev
cd ~/dev
git clone https://github.com/<ТВІЙ_НІК>/claude-team-kit.git
```

Тепер кіт лежить у `~/dev/claude-team-kit`.
⚠️ **Не видаляй і не переміщуй цю теку.** Claude читає налаштування саме звідти.

### A3. Встанови

```bash
cd ~/dev/claude-team-kit
bash install.sh --link
```

Що зробила ця команда:
| Куди | Що | Навіщо |
|---|---|---|
| `~/.claude/agents/` | посилання на 7 агентів `team-…` | Claude Code бачить їх у всіх проєктах |
| `~/.claude/commands/` | посилання на команди `/feature`, `/pipeline-init-web`, … | щоб з'явились слеш-команди |
| `~/.claude/pipeline/` | посилання на «двигун» `pipeline.mjs` і правила | точні операції: гілки, перевірки, коміти |
| `~/.claude/settings.json` | охоронець + дозволи | блокує `git push`, читання `.env` тощо |
| `~/.claude/CLAUDE.md` | блок «відповідай українською» | Claude відповідає українською в усіх сесіях |

`~/.claude` — це загальна тека Claude Code для твого користувача на цьому Mac. Твої власні налаштування в ній не перезаписуються, а від змінених файлів робляться копії `.bak.<час>`.

### A4. Перевір

```bash
node ~/.claude/pipeline/pipeline.mjs doctor
```

✅ Має бути `✔ node …`, `✔ git …`, `✔ guard hook installed`.
⚠️ Рядок `no .pipeline/workspace.json here` зараз нормальний: ти не в проєкті.

Потім відкрий Claude Code (`claude` у терміналі; якщо він був відкритий, закрий і відкрий знову):
- напиши `/agents` → у списку має бути 7 агентів `team-…`;
- напиши `/` → у підказках мають бути `/feature`, `/pipeline-init-web`, `/pipeline-init-mobile`.

### A5. Як оновлювати кіт потім

```bash
cd ~/dev/claude-team-kit && git pull && bash install.sh --link
```

Після цього перезапусти Claude Code.

## Частина B. Тільки для мобільних додатків (один раз на комп'ютер)

Якщо робиш лише веб, пропусти цю частину.

### B1. Android Studio (емулятор Android + Java)

1. Скачай і встанови Android Studio: https://developer.android.com/studio
2. Відкрий її → **More Actions → SDK Manager**:
   - вкладка **SDK Platforms**: постав галочку на одній свіжій версії Android (наприклад, Android 15 / API 35);
   - вкладка **SDK Tools**: галочки на **Android SDK Build-Tools**, **Android Emulator**, **Android SDK Platform-Tools** → **Apply**.
3. **More Actions → Virtual Device Manager → Create Device** → вибери, наприклад, Pixel 8 → систему API 35 → **Finish**.
4. Запам'ятай **точну назву** емулятора (AVD). Вона знадобиться в кроці B5.

Java окремо ставити не треба: вона вже є всередині Android Studio (папка `jbr`), і нижче ми просто вкажемо до неї шлях.

### B2. Xcode (симулятор iPhone), тільки на Mac

1. Встанови **Xcode** з App Store (він великий, це займе час).
2. Один раз виконай у терміналі:
   ```bash
   sudo xcode-select -s /Applications/Xcode.app
   xcodebuild -runFirstLaunch
   ```
3. Відкрий Xcode → **Settings → Components** (або **Platforms**) → встанови **iOS** (симулятор).
4. Для React Native потрібен CocoaPods:
   ```bash
   brew install cocoapods
   ```
   Якщо `brew` не знайдено, спершу встанови Homebrew з https://brew.sh.

### B3. Maestro (запускає тести на симуляторі)

```bash
curl -Ls "https://get.maestro.mobile.dev" | bash
```

Він встановиться в `~/.maestro/bin`. Цю команду запускаєш **ти сам**: агентам таке заборонено правилами безпеки.

### B4. Пропиши шляхи в `~/.zshenv`

Термінал на Mac (zsh) читає файл `~/.zshenv` при кожному запуску, і Claude Code теж. Там ми скажемо, де лежать Java, Android-інструменти і Maestro.
`~/.zshenv` — це не тека, а прихований **файл** у домашній теці (`/Users/<твоє-імʼя>/.zshenv`). Якщо його ще немає, це нормально.

1. Створи (якщо його немає) і відкрий файл:
   ```bash
   touch ~/.zshenv && open -e ~/.zshenv
   ```
   `touch` створює файл, тільки якщо його ще немає, а якщо він є, нічого в ньому не змінює. `open -e` відкриває файл у TextEdit.

2. Встав у кінець файлу цей блок:
   ```sh
   # Claude Team Kit — інструменти для мобільних тестів
   export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
   export ANDROID_HOME="$HOME/Library/Android/sdk"
   export PATH="$PATH:$HOME/.maestro/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$JAVA_HOME/bin"
   ```
   Що це означає:
   - `JAVA_HOME` — де лежить Java (та, що вбудована в Android Studio). Вона потрібна Maestro і збірці Android.
   - `ANDROID_HOME` — де Android Studio тримає SDK.
   - `PATH` — список тек, де термінал шукає команди. Ми додаємо туди `maestro`, `adb` і `emulator`.

3. Збережи: `Cmd + S`. Якщо TextEdit пропонує формат, файл має лишитися **простим текстом** (меню **Format → Make Plain Text**).

4. Закрий **усі** вікна терміналу і відкрий новий. Якщо Claude Code був запущений, перезапусти і його.

### B5. Перевір мобільні інструменти

У новому вікні терміналу:

```bash
java -version                         # має показати версію 17 або новішу
adb version                           # Android Debug Bridge …
emulator -list-avds                   # назва твого емулятора, напр. Pixel_8_API_35
maestro --version                     # версія Maestro
xcrun simctl list devices available   # список симуляторів iPhone (тільки Mac)
```

Запиши дві назви, вони підуть у налаштування проєкту:
- **назва емулятора Android** з `emulator -list-avds`, наприклад `Pixel_8_API_35`;
- **назва симулятора iPhone** з `xcrun simctl list devices available`, наприклад `iPhone 16`.

Якщо якась команда пише `command not found`, дивись [Частину G](#частина-g-якщо-щось-не-працює).

## Частина C. Один раз на кожен проєкт

### C1. Підготуй теку проєкту

Структура може бути будь-яка. Головне, щоб усе було в одній теці (воркспейсі):

```
myapp/                    ← сюди заходиш і тут запускаєш claude
├── backend/              ← або services/users, services/orders …
├── web/                  ← сайт (якщо є)
└── mobile/               ← React Native / Expo додаток (якщо є)
```

Кожна підтека може бути окремим git-репозиторієм або частиною одного спільного.

**Новий проєкт:**
```bash
mkdir ~/projects/myapp && cd ~/projects/myapp
git init
# створи або склонуй сюди backend/, web/, mobile/ …
git add -A && git commit -m "init"
```

**Існуючий проєкт:**
```bash
cd ~/projects/myapp
git add -A && git commit -m "save before pipeline"
```
Пайплайн не стартує, якщо є незбережені зміни. Тому спершу закоміть.
Якщо в підтеці окремий репозиторій, закоміть і там.

### C2. Підключи проєкт до агентів

```bash
cd ~/projects/myapp
claude
```

Всередині Claude напиши **одну** команду:

```
/pipeline-init
```

Вона універсальна: сама проходить по всіх папках і знаходить сайти, мобільні додатки, бекенди, воркери, інфраструктуру й сабмодулі. Потім **зв'язує проєкти між собою** (хто кого викликає) і кожному налаштовує власне тестування.

Якщо хочеш налаштувати тільки одну частину, є вузькі варіанти: `/pipeline-init-web` (лише сайт + бекенди) і `/pipeline-init-mobile` (лише додаток + бекенди). Будь-яку з команд можна запускати повторно: вона доповнює маніфест і нічого не стирає.

Що буде далі: Claude покаже таблицю сервісів, **схему зв'язків** (наприклад `mobile → api`, `web → api`) і що треба перевірити, а також поставить до 4 питань. Для мобільного він ще перевірить назви симулятора й емулятора з кроку B5. Після твого «ок» він створить:

| Що | Навіщо |
|---|---|
| `.pipeline/workspace.json` | «паспорт» проєкту: які сервіси, де лежать, як перевіряти і деплоїти |
| `docs/specs/_TEMPLATE.md` | шаблон ТЗ, за яким Оркестратор пише задачі |
| `contracts/` | опис API між бекендом і клієнтами |
| `e2e/` | веб-тести Playwright |
| `e2e-mobile/` | мобільні сценарії Maestro |
| рядки в `.gitignore` | щоб тимчасові файли пайплайну не потрапляли в git |

### C3. Доустанови тестові інструменти проєкту

**Для веб-тестів** (Claude запропонує те саме):
```bash
cd e2e
npm init -y
npm i -D @playwright/test typescript
npx playwright install chromium
cd ..
```

**Для мобільного** запусти smoke-тест: він доводить, що збірка, встановлення і Maestro працюють. `/pipeline-init-mobile` запропонує його в кінці, просто погодься. Перша збірка iOS може йти 10–20 хвилин, це нормально.

### C4. Перевір і закоміть

```bash
node ~/.claude/pipeline/pipeline.mjs doctor
git add -A && git commit -m "add claude team pipeline"
```

✅ У `doctor` біля кожного сервісу має бути `✔`. Попередження `no lint/typecheck/test` означають, що в сервісі немає таких npm-скриптів. Агенти працюватимуть, але перевірок буде менше. Варто їх додати.

## Частина D. Щоденна робота

У теці проєкту запусти `claude` і пиши задачі так:

```
/feature Користувач може змінити email у профілі (веб і мобільний), з підтвердженням паролем
```

Агенти самі пройдуть етапи і писатимуть статус українською:

```
[1/6] план: docs/specs/change-email.md — сервіси users, web, mobile
[2/6] розробка: users ✔ → web ✔, mobile ✔
[3/6] претестер: BLOCK (1 blocker — немає перевірки власника) → виправлення 1/3
[3/6] претестер: PASS
[4/6] QA: веб PASS 4/4, мобільний PASS 4/4 (iOS + Android)
[5/6] перевірка і коміт: users 1a2b3c4, web 5d6e7f8, mobile 9a0b1c2
```

**Пушиш ти сам**, коли переглянеш результат: `git push` у потрібних репозиторіях.

### Два способи працювати

**1. Повний ланцюжок:** `/feature <опис>` робить усе від ТЗ до коміту.

**2. Точкове керування:** ти сам кажеш, що і кому робити. Наприклад:

```
/plan Авторизація через email і пароль          ← тільки ТЗ, без коду; ти переглядаєш
/assign backend зроби ендпоінти з ТЗ              ← конкретне завдання бекендеру
/assign mobile зроби екрани Login і Register      ← мобільному розробнику
/test mobile                                      ← прогнати тести на симуляторі
/fix-after-testing                                ← виправити все, що впало в тестах
/test android                                     ← перевірити ще раз тільки Android
/commit                                           ← перевірити все, що застаріло, і закомітити
```

Можна змішувати: почати з `/feature`, а коли тести впали, дати `/fix кнопка Save ховається під клавіатурою на iPhone SE`.

### Команди

| Команда | Що робить |
|---|---|
| `/feature <опис>` | нова задача від ТЗ до коміту, повністю автоматично |
| `/plan <опис>` | тільки план: ТЗ, контракти, критерії. Код не пишеться, ти переглядаєш і вирішуєш далі |
| `/assign <роль> <що зробити>` | пряме завдання одному агенту: `backend`, `web`, `mobile`, `qa`, `qa-mobile`, `претестер`, `інфра` |
| `/test [що]` | тільки тести, без виправлень: `unit`, `lint`, `typecheck`, `comments`, `web`, `api`, `mobile`, `ios`, `android`, `review`, `all` |
| `/fix-after-testing` | виправити все, що впало в останніх тестах (веб і/або симулятор), і перепрогнати ці тести |
| `/fix <опис проблеми>` | виправити описану тобою проблему (або все, що впало в будь-яких звітах), потім перевірити |
| `/verify [кроки] [сервіс]` | перевірки коду: коментарі, lint, typecheck, тести, build |
| `/commit` | довести задачу до коміту: перепрогнати все застаріле (ревʼю претестера, тести, verify) і закомітити. `/commit fix` — з автовиправленнями |
| `/resume <задача>` | продовжити задачу повним ланцюжком з місця, де вона зупинилась |
| `/pipeline-status` | що зараз у роботі, де зупинилось |
| `/pretest` | тільки ревʼю претестера (патерни, антипатерни, баги, безпека): поточної задачі або незакомічених змін; однаково в Claude, Gemini, Codex (Частина U) |
| `/deploy <середовище> [задача]` | деплой за налаштуваннями (production — тільки після твого «так») |

**Яка задача?** Якщо не вказати назву, команда бере поточну, тобто останню незавершену (`pl current`). Якщо задачі немає, а ти просиш змінити код, оркестратор сам створить маленьку задачу, наприклад `fix-login-android`.

**Помилка в іншому проєкті?** Наприклад, тест мобільного впав, а причина в бекенді. Тоді оркестратор додасть бекенд до задачі (`pl add`) і передасть виправлення бекендеру.

**Захист нікуди не дівається.** Після будь-якого виправлення старі результати перевірок стають недійсними. `/commit` сам побачить, що застаріло (безпека, тести чи verify), і перепрогонить саме це. Закомітити код, який не пройшов перевірки після останньої зміни, неможливо.

### Codex у панелі VS Code: запасний режим `--inline`
Пісочниця Codex може не дозволяти вкладений запуск (`codex exec` усередині Codex: немає мережі). Тоді `pl run … --inline` лише готує файл ролі й друкує `RUN_INLINE`, а ПМ виконує роль сам у тому ж вікні за цим файлом. Поведінка та сама, але без ізоляції контексту (сліпі ролі менш сліпі). ПМ вмикає цей режим сам, якщо звичайний запуск дав `PERMISSIONS`/`AUTH`.

## Частина E. Що де лежить і що куди вписувати

### Файли на твоєму комп'ютері (не в проєкті)

| Файл / тека | Що там | Чи треба редагувати |
|---|---|---|
| `~/dev/claude-team-kit/` | сам кіт (твій git-репо) | так, якщо хочеш змінити агентів чи правила; потім `git push` |
| `~/.claude/agents/`, `commands/`, `pipeline/` | посилання на кіт | ❌ ні, їх створює `install.sh` |
| `~/.claude/settings.json` | охоронець і дозволи Claude Code | зазвичай ні |
| `~/.claude/CLAUDE.md` | твої загальні правила для Claude + блок «українською» | можна дописувати свої правила **поза** блоком `claude-team-kit` |
| `~/.zshenv` | шляхи до Java, Android, Maestro | один раз (крок B4) |

### Файли в проєкті

| Файл | Хто створює | Що вписувати руками |
|---|---|---|
| `.pipeline/workspace.json` | `/pipeline-init-…` | виправляти, якщо Claude щось визначив не так (див. нижче) |
| `<сервіс>/CLAUDE.md` | ти (необов'язково) | правила саме цього сервісу: бібліотеки, патерни, стиль |
| `docs/testing/<сервіс>.md` | ти разом з `/pipeline-init` (рекомендовано) | опис додатку для тестера: для чого він, хто користується, що критично, де ламається, тестові акаунти (див. частину J) |
| `e2e/`, `e2e-mobile/` | тестери | нічого, це «зошит» тестерів: сценарії по задачах |
| `docs/specs/*.md` | Оркестратор | нічого, але можна читати і правити ТЗ |
| `.pipeline/<задача>/` | пайплайн | нічого — звіти, diff, скріншоти тестів |

### Головні поля `workspace.json`

Повний приклад: `node ~/.claude/pipeline/pipeline.mjs template workspace`.

**Мова і коментарі:**
```json
"conventions": {
  "replyLanguage": "uk",
  "comments": { "language": "uk", "level": "all", "enforce": true },
  "extra": ["Усі суми зберігаємо в копійках (integer)."]
}
```
- `replyLanguage` — мова відповідей і статусів;
- `comments.level`: `all` = коментар до кожної функції і змінної; `functions` = лише функції, класи і змінні верхнього рівня;
- `extra` — будь-які правила проєкту, їх отримають усі агенти.

**Моделі за ШІ (необов'язково):**
```json
"models": { "gemini": { "deep": "<назва>" }, "codex": { "fast": "<назва>", "std": "<назва>", "deep": "<назва>" } }
```
Рівні `fast` / `std` / `deep` для Gemini і Codex (Claude свої знає). Для всіх проєктів одразу: `~/.claude/team-kit-models.json`. Деталі: Частина U.

**Сервіс (бекенд або веб):**
```json
{
  "name": "users",
  "type": "backend",
  "path": "services/users",
  "stack": "Node 20 + Express + TypeScript + PostgreSQL",
  "commands": { "lint": "npm run lint", "typecheck": "npx tsc --noEmit", "test": "npx vitest run", "build": "npm run build" },
  "dev": { "start": "npm run dev", "url": "http://localhost:3001/health" }
}
```
- `type`: `frontend` (сайт), `mobile` (додаток), `backend`, `worker`, `library`, `infra`;
- `commands` — як перевірити сервіс (виконується в його теці);
- `dev` — як запустити його локально для тестів і за якою адресою перевірити, що він живий;
- `dependsOn` — **зв'язки**: від яких сервісів цей залежить (кого він викликає). Приклад для додатку: `"dependsOn": ["api"]`.

**Зв'язки між проєктами (`dependsOn`)**

`/pipeline-init` знаходить їх сам, тобі лишається перевірити:
- за адресами в конфігах: якщо в `mobile/.env.example` є `http://localhost:4000`, а бекенд працює на `4000`, то `mobile → api`;
- за назвами змінних: `USERS_SERVICE_URL` означає зв'язок із сервісом `users`;
- за `depends_on` у `docker-compose.yml`.

Навіщо вони потрібні:
| Де | Що дають |
|---|---|
| План задачі | змінюється API бекенду → оркестратор бачить, які клієнти теж треба оновити |
| Порядок розробки | спершу той, хто надає API, потім ті, хто його використовує; незалежні — паралельно |
| Тести | веб-тести піднімають сайт і лише його бекенди; мобільні — лише бекенди додатку |

Подивитись: `pl services` → колонки **uses** і **used by**.

**Тестування кожного проєкту**
| Тип | Своє тестування |
|---|---|
| усі | `commands`: lint, typecheck, test, build — у своїй теці під час verify |
| `frontend` (сайт) | + Playwright у браузері (`e2e/`, агент `team-qa`) |
| `mobile` | + Maestro на iOS-симуляторі й Android-емуляторі (`e2e-mobile/`, агент `team-qa-mobile`) |
| `backend` / `worker` | + API-тести (`team-qa`) і перевірка через клієнтів, які від нього залежать |

**Мобільний додаток** — тут найчастіше треба вписати свої значення:
```json
{
  "name": "mobile",
  "type": "mobile",
  "path": "mobile",
  "commands": { "lint": "npm run lint", "typecheck": "npx tsc --noEmit", "test": "npx jest --ci" },
  "mobile": {
    "framework": "expo",
    "platforms": ["ios", "android"],
    "appId":  { "ios": "com.bohdan.myapp", "android": "com.bohdan.myapp" },
    "device": { "ios": "iPhone 16", "android": "Pixel_8_API_35" },
    "build": {
      "ios": "npx expo run:ios --configuration Release --no-bundler --device \"{device}\"",
      "android": "npx expo run:android --variant release --no-bundler"
    }
  }
}
```
| Поле | Де взяти значення |
|---|---|
| `appId.ios` | `app.json` → `expo.ios.bundleIdentifier` |
| `appId.android` | `app.json` → `expo.android.package` |
| `device.ios` | точна назва з `xcrun simctl list devices available` |
| `device.android` | точна назва з `emulator -list-avds` |
| `build` | для Expo як вище; для «голого» RN: `npx react-native run-ios --mode Release --simulator "{device}" --no-packager` і `npx react-native run-android --mode release --no-packager` |
| `platforms` | `["ios","android"]` на Mac, `["android"]` на Windows/Linux |

**Деплой** (необов'язково):
```json
"deploy": {
  "environments": {
    "staging":     { "steps": [{ "name": "up", "cwd": "infra", "run": "docker compose up -d --build" }],
                     "healthchecks": ["http://localhost:3000/health"],
                     "rollback": [{ "name": "down", "cwd": "infra", "run": "docker compose down" }] },
    "production":  { "requireApproval": true, "steps": [{ "run": "gh workflow run deploy.yml" }] },
    "mobile-store":{ "requireApproval": true, "steps": [{ "cwd": "mobile", "run": "npx eas-cli build --profile production --platform all --non-interactive --auto-submit" }] }
  }
}
```
`requireApproval: true` означає, що деплой піде тільки після твого «так» у чаті і підтвердження команди.

## Частина F. Як усе влаштовано

### Команда агентів
| Роль | Веб | Мобільний |
|---|---|---|
| Оркестратор (головна сесія) | ТЗ, контракти, керує всіма | те саме |
| Бекенд | `team-backend` | `team-backend` (той самий) |
| Клієнт | `team-frontend` | `team-mobile` |
| Претестер | `team-reviewer` — досвідчений ревʼюер, бачить тільки diff, без ТЗ | + мобільний чекліст |
| Тести | `team-qa` — Playwright у браузері | `team-qa-mobile` — Maestro на симуляторі |
| Інфра | `team-backend` у режимі infra (Docker, CI); коміт, відкат і деплой виконує ПМ скриптами | + EAS build/submit |

### Етапи задачі
1. **План.** Оркестратор пише ТЗ і контракти. Нова гілка **не створюється**: робота йде в поточній гілці кожного репозиторію (де ти зараз стоїш).
2. **Розробка.** Спершу бекенди, потім сайт і додаток (паралельно), потім інфраструктура.
3. **Претестер.** Бачить **тільки** зміни коду, без ТЗ і переписки, і оцінює, чи все написано правильно: патерни, антипатерни, баги, безпека. Іде паралельно з тестувальником.
4. **Тести.** Веб тестується в браузері. Мобільний на симуляторі: скрипт вмикає симулятор, піднімає бекенди, збирає додаток (тільки якщо код змінився), проганяє сценарії і робить скріншоти. Агент переглядає скріншоти і лог.
5. **Перевірка і коміт.** Спершу коментарі українською, потім lint → typecheck → test → build, і коміт у кожному репозиторії.
6. **Деплой.** Тільки якщо ти попросив.

### Що гарантує скрипт (а не обіцянка агента)
- Коміт можливий тільки після PASS ревʼю претестера, тестів і перевірки (знахідки, прийняті як компроміс, не блокують).
- Якщо код змінився після перевірок, коміт відхиляється.
- Функція чи змінна без коментаря українською не пройде перевірку.
- `.env`, ключі (`*.pem`, `*.key`, `*.p12`) і файли понад 1 MB не комітяться.
- Максимум 3 спроби виправлення, далі відкат через `git stash` (роботу можна відновити).
- `git push`, `reset --hard`, `git clean`, читання `.env` і `curl | sh` заблоковані (тільки в теках з `.pipeline/workspace.json`).
- Production-деплой можливий тільки після твого підтвердження.

### Чесно про обмеження
- Те, що агент пише тільки «у свою» теку, тримається на інструкції. Порушення видно в diff.
- Перевірка коментарів спрощена: більшість випадків ловить, але дуже нестандартний код може пропустити.
- iOS-симулятор працює тільки на Mac.
- Push-сповіщення, камера, покупки й біометрія на симуляторі не тестуються: агент позначає їх як `manual`.
- Великі задачі (diff понад 3000 рядків) дорожчі й менш точні, краще ділити.

## Частина M. Як проходить задача (команда з п'яти ролей)

Ти спілкуєшся лише з **ПМ** (головний чат). Решта ролей працює «за лаштунками», а ПМ звітує тобі.

| Роль | Агент | Що робить | Чого НЕ бачить |
|---|---|---|---|
| **ПМ** | головна сесія | ставить уточнюючі питання, питає глибину тестування, пише ТЗ (з назвами `testID`), розподіляє роботу, звітує | не пише код |
| **Дизайнер** | `team-designer` | запускається **лише для візуальних змін** (новий екран, редизайн, «зроби гарніше»): вивчає дизайн-мову проєкту, проєктує з точними токенами, станами й текстами, сам рендерить макет і дивиться на нього, пише `docs/design/<id>.md` для розробників | коду застосунку (не редагує) |
| **Розробники** | `team-backend`, `team-frontend`, `team-mobile` | виконують ТЗ; є питання, ставлять їх ПМ, а той тобі | не спілкуються з претестером і тестувальником напряму |
| **Претестер** | `team-reviewer` | досвідчений ревʼюер: патерни, антипатерни, баги, безпека; оцінює лише код | ТЗ і переписку |
| **Тестувальник** | `team-qa` / `team-qa-mobile` | e2e у браузері чи на симуляторі/емуляторі за ТЗ; вмикає і сценарії, що можуть зламати фічу; глибина: поверхнево / поглиблено / дуже ретельно | код і звіти розробників |

DevOps немає: коміт, відкат і перевірки виконує ПМ готовими скриптами; інфраструктурні файли (Docker, CI) пише бекенд-агент.

**Хід задачі:**
1. ПМ ставить до 6 уточнюючих питань і питає глибину тестування (з орієнтовним часом).
2. ПМ пише ТЗ: критерії, що тестувати, точні `testID`.
3. Розробники пишуть код (бекенд → веб/мобільний). Питання йдуть через ПМ тобі.
4. Паралельно: претестер дивиться код, тестувальник проходить фічу за ТЗ.
5. Є зауваження → ПМ відправляє їх **потрібному розробнику**, той виправляє, перевіряється лише те, що було не так.
6. Перевірки (lint, типи, тести, збірка, коментарі) і коміт.
7. ПМ пише тобі підсумок: що зроблено, які були зауваження, прийняті компроміси, що впало.

**Максимум 3 спроби виправлення** для кожного виду (ревʼю, тести, перевірка). Якщо не вдалось: відкат, звіт «не вдалося» з причиною.

### Гілки: працюємо там, де ти стоїш
Перед `/feature` переключи потрібну гілку (`git switch staging`) у кожному репозиторії. Кіт **не створює** нових гілок і комітить прямо в поточну. Якщо репозиторій на `main` / `master`, скрипт попередить. Під час задачі гілку міняти не можна: коміт це перевіряє.
Хочеш стару поведінку з окремою гілкою `feat/<задача>`? У `workspace.json` у блоці `pipeline` постав `"branchMode": "feature"`.

### Як не зациклитись із претестером
Претестер бачить код сліпо і може вимагати те, що фізично змінити неможливо (бібліотека, фреймворк, готовий контракт). Щоб це не крутилося по колу:
- **Знахідки мають рівні:** `blocker` (зламає прод, діра в безпеці, втрата даних) завжди блокує; `major` (явний антипатерн) блокує лише в перших двох раундах, потім стає техборгом; `minor` / `info` не блокують ніколи.
- **Лише новий код.** Проблеми в старому коді, якого не торкались, не блокують.
- **Кожна вимога має вихід:** мінімальне виправлення і «що ще мене влаштує».
- **Без нових вимог на кожному раунді:** з 2-го раунду претестер перевіряє тільки раніше знайдене і нові проблеми від самих виправлень.
- **Розробник може заперечити:** `CANNOT_FIX` з причиною та альтернативою. ПМ порівнює альтернативу з тим, що влаштувало б претестера, і приймає компроміс (`pl waive`). Для `blocker` ПМ **не** вирішує сам: питає тебе («виправити», «прийняти ризик», «зупинити»).
- Усі прийняті компроміси та техборг ПМ виписує в підсумковому звіті.

Загальна діагностика: `node ~/.claude/pipeline/pipeline.mjs doctor`. Запускай у теці проєкту, і він покаже, що саме не так.

## Частина H. Усі команди

Команди бувають трьох видів:
1. **Слеш-команди**: пишеш у чаті Claude Code (`/feature …`). Це основний спосіб роботи.
2. **Команди двигуна** `pipeline.mjs`: виконуються в терміналі. Здебільшого їх запускають самі агенти, але ти теж можеш, щоб щось перевірити.
3. **Скрипти встановлення**: `install.sh` / `uninstall.sh`.

### H1. Слеш-команди (у чаті Claude Code)

| Команда | Коли використовувати | Приклад |
|---|---|---|
| `/pipeline-init` | один раз на проєкт: **сам знаходить усе** (сайт, мобільний, бекенди, воркери, інфра, сабмодулі), зв'язує проєкти і налаштовує кожному тестування | `/pipeline-init` |

| `/feature <опис>` | нова задача: питання → ТЗ → код → претестер + тести → коміт | `/feature Додати зміну email у профілі` |
| `/plan <опис>` | тільки план і ТЗ, без коду | `/plan Авторизація через email` |

## Частина L. Швидкість тестування

> Тестувальник тепер працює «очима» і має жорсткий ліміт часу (Частини J і K), тож основна економія вже там. Ця частина стосується швидкості **збірки** застосунку на симуляторі (швидкий режим, кеш збірки), і вона діє й далі. Команди `pl sim` лишаються для регресійних прогонів.

Фіча на 15–20 хв не повинна тестуватись 2 години. Ось що забирало час і що змінено:

| Що гальмувало | Що тепер |
|---|---|
| Release-збірка додатку після **кожної** зміни коду (iOS 10–20 хв) | **Швидкий режим** (`"mode": "fast"`): debug-збірка робиться один раз, JS-зміни підтягуються через Metro **без перезбірки**. Перезбірка тільки при зміні нативних частин (`ios/`, `android/`, `app.json`, нові нативні модулі) |
| Обидві платформи на кожну задачу | `поверхневе` і `поглиблене` тестують **одну основну** платформу (iOS на Mac), `дуже ретельне` тестує обидві |
| Після кожного виправлення прогін **усіх** сценаріїв | `--rerun-failed`: тільки впалі + нові + «happy»-сценарії, якщо змінився код. Решта результатів зберігається |
| Тестувальник писав усі сценарії наосліп, потім багато разів виправляв селектори | спершу дивиться на екран (`pl screen`), пише 2–3 сценарії, перевіряє, потім решту |
| Дослідницька сесія без обмежень | ліміт часу: поглиблене ~5 хв, дуже ретельне ~15 хв на платформу |
| Ревʼю і тести по черзі | претестер і тестувальник йдуть **паралельно** |
| Тестувальник на Opus (повільно) | тестувальники на **Sonnet**: швидше пише YAML, а ретельність гарантує довідник + перевірка покриття. Розробники лишаються на Opus |

Орієнтовний час тестування (коли збірка вже є):

| Рівень | Час |
|---|---|
| Поверхневе | ~5–15 хв |
| Поглиблене | ~20–40 хв |
| Дуже ретельне | ~1–2 год (обидві платформи, усі категорії) |

Порада: для щоденних фіч бери **поглиблене**, а **дуже ретельне** запускай перед релізом (`/test regression дуже ретельно`).

### Як увімкнути швидкий режим, якщо проєкт уже підключений
Найпростіше: запусти `/pipeline-init` ще раз, і він запропонує перевести мобільний на швидкий режим. Або попроси в чаті: «переведи мобільний на fast-режим тестування».

У `workspace.json` це виглядає так (Expo):
```json
"mobile": {
  "mode": "fast",
  "build": {
    "ios": "npx expo run:ios --configuration Debug --no-bundler --device \"{device}\"",
    "android": "npx expo run:android --variant debug --no-bundler"
  },
  "metro": { "start": "npx expo start --port 8081", "url": "http://localhost:8081/status" },
  "rebuildOn": "native"
}
```
І в додатку сховай попередження розробника (жовті плашки) під час тестів, бо вони можуть перекривати кнопки:
```ts
// Ховаємо LogBox під час автотестів, щоб плашки не перекривали елементи
if (process.env.EXPO_PUBLIC_E2E === '1') LogBox.ignoreAllLogs();
```

⚠️ Якщо в додатку є `expo-dev-client`, швидкий режим не підходить: debug-збірка відкриває екран вибору сервера, і тести «спотикаються». Тоді лишається release-режим.

### Інші налаштування
```json
"qa": {
  "defaultDepth": "ask",
  "platformsByDepth": { "smoke": ["ios"], "deep": ["ios"], "exhaustive": ["ios", "android"] },
  "retest": "failed+smoke"
}
```
- `platformsByDepth` — які платформи тестувати на кожному рівні;
- `retest`: `failed+smoke` (за замовчуванням) — після зміни коду обов'язково перепрогнати впалі й «happy»-сценарії; `all` — усі (повільніше, надійніше);
- `mobile.primaryPlatform` — основна платформа для поверхневого й поглибленого.

## Частина K. Ретельність тестів, питання від агентів, планка якості

### Опитування: наскільки ретельно тестувати
Ще в PLAN ПМ питає тебе (кнопками в Claude, текстом у Gemini/Codex), чи потрібен тестувальник узагалі: варіанти «не потрібен» (ворота QA для задачі вимикаються), «поверхнево», «поглиблено», «дуже ретельно». Кожен рівень має **жорсткий ліміт часу** (його видає `pl eyes`, після нього дії відхиляються):

| Рівень | Час | Що перевіряється | Мінімум на кожен критерій |
|---|---|---|---|
| **Поверхневе** (`smoke`) | ≤ 8 хв | працює чи ні; веб: верстка на 3 ширинах | 1 перевірка |
| **Поглиблене** (`deep`) | ≤ 20 хв | + неправильні дані, межі, стани; веб: верстка на 7 ширинах; мобільне: переривання | 2 перевірки |
| **Дуже ретельне** (`exhaustive`) | ≤ 45 хв на платформу | + навігація, переривання, мережа, доступність, вигляд; веб: 13 ширин; мобільне: обидві платформи | 4 перевірки |

Ліміти можна змінити: `"qa": { "budgetMin": { "smoke": 8, "deep": 20, "exhaustive": 45 } }`. Перша збірка застосунку на симуляторі (10–20 хв) в ліміт не входить, вона робиться один раз.

Щоб не питав щоразу:
- одразу в задачі: `/feature … тестування дуже ретельне` (або «без тестувальника») чи `/test mobile поглиблено`;
- або назавжди в `workspace.json`: `"qa": { "defaultDepth": "deep" }`. Значення `"ask"` означає «питати щоразу».

### Що робить тестувальник
Це не скриптер, а людина з «очима» (Частина J): сам відкриває справжній браузер чи симулятор, дивиться на скріншоти, користується застосунком, ламає його навмисно. Метод: **місії → дія → подивитись → вирішити**. Довідник `pl playbook` дає каталог того, що пробувати (форми, поля, жести, переривання, мережа, стани, доступність, верстка на ширинах, збіг з листом).

### Скрипт перевіряє ретельність
`pl coverage` перевіряє **звіт тестувальника проти журналу його дій**. Штамп (без нього коміт не пройде) ставиться лише коли:
- кожен доказ у звіті (скріншот, лист, порівняння) справді створений інструментами `pl eyes` / `pl mail` / `pl compare` і є в журналі (підробити не вийде);
- на кожен критерій із ТЗ є мінімум перевірок для рівня і покрито обов'язкові категорії (або для категорії вказана **конкретна причина**, чому вона не підходить);
- веб: верстку реально перевірено на потрібній кількості ширин;
- кожен пункт `K-n` з розділу ТЗ **Consistency** перевірено (додаток ↔ лист).

Якщо після тестування ти підняв рівень, наприклад з поглибленого на дуже ретельне, коміт не пройде, поки тести не доповнять до нового рівня.

### Питання від агентів замість здогадок
Розробники й тестувальники **не вгадують**. Якщо щось впливає на дані, API, поведінку для користувача, безпеку чи підхід, агент:
1. робить те, що від відповіді не залежить;
2. зупиняється з `STATUS: QUESTIONS`: питання + «чому це важливо» + варіанти + своя рекомендація.

ПМ збирає питання від усіх агентів етапу і ставить їх тобі **одним блоком**, кнопками, з рекомендацією на першому місці. Твої відповіді записуються в ТЗ (розділ **Decisions**), тому вдруге те саме не питатимуть. Далі агенти продовжують.

Дрібниці, де є очевидний варіант за замовчуванням, агент вирішує сам, але показує їх як `ASSUMPTIONS`. Ти бачиш їх у статусі і можеш заперечити через `/fix`.

Якщо ти не біля комп'ютера (запуск за розкладом), ПМ бере рекомендацію агента, позначає її як «прийнято без тебе» і показує в підсумку.

### «Працівники місяця»
Усі агенти працюють за спільною планкою якості (`pl conventions`, розділ 3):
- спершу розібратися: ТЗ, контракти, код, хто викликає те, що змінюється;
- обробити **всі** шляхи, а не лише щасливий: порожньо, помилки, таймаути, великі/малі дані;
- тест на кожну гілку логіки; виправлення бага починається з тесту, що його ловить;
- жодного `console.log`, закоментованого коду, зайвих `TODO`, `any` без пояснення;
- **самоперевірка перед «готово»**: агент перечитує свій diff як прискіпливий рев'юер за чек-листом (критерії, крайні випадки, безпека, стиль, коментарі, усі перевірки зелені) і пише у звіті, що перевірив;
- чесний звіт: що зроблено, що ні, у чому не впевнений.

### Які моделі працюють (у Claude; для Gemini і Codex див. Частину U)

| Роль | Модель | Що робить |
|---|---|---|
| **ПМ** (твій чат) | середня модель ШІ (Claude: **Sonnet**; `/model opus` лише для планування задачі L) | план і завдання |
| Розробники `team-backend`, `team-frontend`, `team-mobile` | **Sonnet** | пишуть код |
| Розвідник `team-scout` | **Haiku** | шукає в коді, збирає контекст |
| Претестер `team-reviewer` | **Sonnet**, на задачі L автоматично **Opus** | перевіряє код |
| Дизайнер `team-designer` | **Opus** на M/L, Sonnet на S | проєктує вигляд (запускається лише для візуальних змін) |
| Тестувальники `team-qa`, `team-qa-mobile` | Sonnet | тестують (швидше, ніж на Opus); у Gemini/Codex ті самі інструкції (Частина U) |

**Модель ПМ задається не агентом, а твоєю сесією.** ПМ це головний чат: рекомендовано **Sonnet** (економія ліміту), а `/model opus` вмикай лише для планування задачі рівня L. Під час виклику агентів ПМ передає параметр `model` з `pl model` (він перекриває `model:` у `agents/*.md`, див. Частину S). Моделі субагентів кіт виставляє сам: це рядок `model:` у файлі `agents/team-<роль>.md` (`opus`, `sonnet` або `haiku`), змінюй його там, якщо захочеш інакше.

Розвідник працює перед ТЗ і пише `.pipeline/<задача>/context.md`: де буде робота, які патерни вже є в проєкті, контракти, тести поруч, ризики. ПМ читає тільки цей файл, а розробникам вказує на нього.

## Частина U. Один набір у Claude Code, Gemini і Codex

**Принцип.** Кожну задачу ти ведеш цілком в одному ШІ, у його власному вікні: Claude Code, Gemini (Antigravity `agy`) або Codex (ChatGPT). Ролі, правила, ворота, команди й формат відповідей **однакові**, змінюється лише спосіб виклику ролей. Розподілу «розробник у Claude, тестувальник у Gemini» більше немає. Підтримки DeepSeek/Kimi теж немає.

### Що однакове скрізь
- Слеш-команди: `/pipeline-init`, `/feature`, `/fix`, `/plan`, `/resume`, `/assign`, `/test`, `/verify`, `/commit`, `/pretest` та інші. У Gemini (agy) і Codex це скіли (`SKILL.md`), які `install.sh` генерує з тих самих файлів `commands/*.md`. Виклик: `/feature …` у Claude і Gemini, `$feature …` (або `/skills`) у Codex.
- Правила ПМ (`pl rules`), ролі (`agents/*.md`), двигун (`pl …`), ворота коміту, стан у `.pipeline/<id>/`.
- Тому задачу можна почати в Claude, а коли скінчиться ліміт, відкрити Gemini або Codex і написати `/resume <id>`: весь прогрес на диску.

### Як ШІ визначається і як викликаються ролі
| | Claude Code | Gemini (agy) | Codex |
|---|---|---|---|
| Визначення ШІ (`pl who`) | змінні `CLAUDECODE…` | `GEMINI_CLI`, `ANTIGRAVITY_*` | `CODEX_THREAD_ID`, `CODEX_SANDBOX` |
| Виклик ролі | сабагент (Agent tool) | `pl run <роль> <id> --prompt "…"` | те саме |
| Модель | `pl model` → haiku / sonnet / opus | `run` обирає сам (flash / pro) | `run` обирає сам (за замовчуванням CLI) |
| Питання тобі | вікно з варіантами | текст із нумерованими варіантами | те саме |
`pl who` друкує `HOST: claude|gemini|codex|unknown`. Якщо визначити не вийшло, ПМ знає, який він ШІ, і передає `--host`; змінна `TEAM_KIT_HOST` перекриває автовизначення. Довгі ролі в Gemini/Codex ідуть у фоні: `pl run … --bg`, потім `pl run-wait <роль> <id>` (код виходу 10 означає «ще працює, виклич ще раз»). Ролі отримують ті самі інструкції, що й у Claude, плюс правило простих shell-команд (без `|`, `&&`, `;`, `>`), бо монітори Gemini/Codex відхиляють складені команди.

### Моделі за складністю (S / M / L)
ПМ у PLAN ставить `pl mark <id> complexity=S|M|L` (`/fix` за замовчуванням S). Таблиця описує **рівні**, а `pl model all <id>` показує, якою моделлю вони стають у поточному ШІ.
| Роль | S | M | L |
|---|---|---|---|
| `team-scout` | fast | fast | fast |
| `team-backend` / `frontend` / `mobile` | std | std | std (`--core`: deep для ядра) |
| `team-reviewer` | std | std | **deep** |
| `team-designer` | std | deep | deep |
| `team-qa` / `team-qa-mobile` | std | std | std |
| ШІ | fast | std | deep |
|---|---|---|---|
| Claude | haiku | sonnet | opus |
| Gemini | gemini-4-hydrogen-medium | gemini-4-hydrogen-high | gemini-4-neon-high (найсильніше: gemini-4-carbon-high, лише Ultra) |
| Codex | модель за замовчуванням CLI | те саме | те саме |
Назви моделей Gemini взято з відкритих описів agy і не перевірені на твоєму акаунті: `pl setup gemini` порівнює їх зі списком `agy models` і підкаже, що виправити. Для Codex назви не задані (я не знаю твого тарифу): коли підключиш, впиши їх у `~/.claude/team-kit-models.json`:
```json
{ "codex": { "fast": "<назва>", "std": "<назва>", "deep": "<назва>" }, "gemini": { "deep": "<назва>" } }
```
Для одного проєкту те саме можна задати в `workspace.json` у полі `models`.

### Тестувальник: питання в кожній задачі
У PLAN ПМ раз питає: **«Тестувальник потрібен?»**: не потрібен / поверхнево (≤ 8 хв) / поглиблено (≤ 20 хв) / дуже ретельно (≤ 45 хв), з рекомендацією під задачу. Якщо ти вже сказав це в запиті («без тестувальника», «поглиблено»), питання пропускається. «Не потрібен» вимикає ворота QA для цієї задачі (`pl mark <id> qa=none`), претестер і `verify` лишаються.

### Претестер окремою командою
`/pretest [задача]` у будь-якому ШІ. Без аргумента бере поточну задачу, а якщо її нема, незакомічені зміни проти HEAD (`adhoc`). Двигун: `pl pretest <id>` готує diff і друкує точний «сліпий» запит; `pl pretest <id> --run` у Gemini/Codex робить усе сам (diff, ревʼю, вердикт). Претестер не бачить ТЗ і розмови, тому його можна запускати де завгодно, наприклад, коли Claude закінчився.

### Встановлення для Gemini і Codex
`bash install.sh` сам знаходить `agy` і `codex` і ставить для них команди (`~/.gemini/antigravity-cli/skills/`, `~/.agents/skills/`), а для Codex ще й мовний блок у `~/.codex/AGENTS.md`. Окремо: `pl adapt --host gemini,codex` (або `--remove`). Потім один раз `pl setup gemini` (CLI, дозволи, моделі; `--yes` додасть дозволи в `~/.gemini/antigravity-cli/settings.json`, `--probe` перевірить відповідь). Дозволи агента глобальні для всього `agy`, тому команда лише показує, що додасть, поки не скажеш `--yes`.

### Що не перевірено
- Реального запуску ролей у Gemini і Codex за допомогою цього набору: перевірено на фейкових `agy`, інструмент реально викликає `agy -p … --mode accept-edits --model …` і `codex exec …`.
- Змінні для визначення Antigravity (`ANTIGRAVITY_*`) взято з відкритих детекторів; якщо `pl who` у agy скаже `unknown`, це не збій, ПМ передасть `--host gemini`.
- Виклик скілів у Codex (`$feature`) і точне місце глобальних скілів agy: за документацією, не вживу.
- Мобільне тестування (симулятор, Maestro) у Gemini/Codex.

## Частина T. iPhone Duo (складаний iPhone): скіл для дизайнера й розробників

**Що це.** Скіл `iphone-duo` (`skills/iphone-duo/SKILL.md`, ставиться в `~/.claude/skills/`) задає єдині стандарти для всіх задач під складаний iPhone: усі кнопки керування в бічній панелі, анімація її появи, безпечні зони, згин, потрібні нативні пакети. Дані взято з документації Apple (Design for iPhone Duo, Prepare your app for iPhone Duo) і Expo SDK 58.

**Як вмикається.** Лише коли потрібно, щоб не витрачати токени: `pl duo on` (прапорець `targets.iphoneDuo` у `workspace.json`). ПМ на етапі PLAN виконує `pl duo`; якщо там `DUO: on` і задача торкається мобільного UI, дизайнер і `team-mobile` читають скіл. Вимкнено: скіл ніхто не читає.

**Стандарт (коротко).**
1. **Розміри за size classes** (compact/regular, ширина з `useWindowDimensions`), без орієнтації, назви пристрою чи фіксованих ширин. Одна ієрархія на всіх позах, функції не привʼязані до пози.
2. **Усі кнопки керування в бічній панелі.** Спершу нативні елементи Expo Router (`Stack`, `NativeTabs`): iOS сам ставить їх у панель, робить overflow і обхід згину. Власні кнопки, яких там не може бути, йдуть у `ControlRail` (референс-реалізація в `references/control-rail.md`). Текстові кнопки й сегментні перемикачі лишаються в навбарі (виняток Apple).
3. **Анімація панелі:** кнопка випливає з краю панелі (220 мс, ease-out) і зникає назад (160 мс, ease-in). **Зникнення старої й поява нової стартують в одному кадрі**, без очікування: на «назад» кнопки поточного екрана йдуть, а кнопки попереднього одразу запливають. Фіксовані слоти не зсувають колонку; однакова кнопка на двох екранах не анімується. Для «Зменшити рух» лише fade. Цифри це типові значення кита (Apple таймінгів не дає), їх треба оцінити на пристрої.
4. **Безпечні зони:** обидва відступи (left/right), панель ≈ 84 pt, абсолютні елементи зсуваються на `insets.right + 16`, каруселям потрібен кінцевий відступ.
5. **Стан переживає складання й розкладання** (скрол, форми, шторки, обрана вкладка).

**Пакети (`pl duo setup`).** Перевіряє Expo SDK ≥ 58 і ставить відсутні через `npx expo install`: `expo-hinge`, `react-native-safe-area-context`, `expo-status-bar`, `react-native-reanimated`, `react-native-worklets`. З `--all` ще `react-native-reserved-regions` і `@expo/ui` (для двопанельних екранів і точної геометрії згину). `--dry` лише показує команду. SDK нижче 58 я автоматично **не** оновлюю: команда зупиниться з поясненням. Це нативні модулі, тож потрібна нова нативна збірка; розробник її не запускає, а пише в NOTES, і ПМ каже тобі.

**Дизайнер.** У документі дизайну додаються розділи Duo: карта панелі (кнопка → SF Symbol → верх/низ → нативна чи власна → на яких екранах), рух панелі, зони безпечні від згину, крайові випадки (Split View, RTL, Dynamic Island), V-n для тестувальника.

**Перевірка.** `simctl` не вміє складати симулятор (немає команд пози). Закритий (зовнішній) екран тестувальник перевіряє звичайними засобами; решту поз або вручну в Device Hub (кнопки Closed / Partially Open / Open, слайдер кута), або через сторонню утиліту `hinge` (`brew install artemnovichkov/tap/hinge`, використовує приватний інтерфейс, може зламатись після оновлення Xcode). Без неї такі перевірки в звіті мають статус `blocked` із приміткою «manual fold check».

## Частина R. Дизайнер (щоб візуальна частина не була «сухою»)

**Проблема:** розробник будує рівно те, що написано в ТЗ. Якщо там «зроби гарніше», виходить функціонально, але сухо. Дизайнер перетворює смак на числа, стани й точні тексти.

### Коли він запускається
ПМ вирішує на етапі PLAN і фіксує: `pl mark <id> design=yes|no`.
- **Так:** новий екран чи компонент, редизайн, «зроби сучасніше/чистіше», кольори, відступи, типографіка, розкладка, іконки, порожні/завантажувані/помилкові стани, онбординг, анімації, вигляд листа чи PDF. Слова «з дизайнером» чи «онови дизайн» примушують запуск.
- **Ні (не стартує взагалі):** логіка, API, дані, баги, продуктивність, рефакторинг, інфра, тести, зміна лише тексту, виправлення зламаної верстки відносно наявного дизайну. Слова «без дизайнера» вимикають його.
- `/fix` на кшталт «поправ вигляд» теж іде через дизайнера, а звичайний баг (обрізаний текст, накладання) іде одразу розробнику. Окремо: `/assign дизайнер <що>`.

### Що він робить
1. Вчить наявну дизайн-мову за кодом (токени, компоненти, шрифти, іконки, темна тема) і, якщо це зміна наявного екрана, **дивиться на поточний UI** (`pl design-shot <url> --service web`, для мобільного `pl screen`). Веде пам'ять `docs/design/SYSTEM.md`, щоб наступні задачі не вигадували другу мову.
2. Проєктує: ієрархія, ритм відступів, типографіка, ролі кольорів, стани, рух, мікротекст (усіма мовами задачі), доступність (контраст з розрахунком).
3. Будує `docs/design/<id>/mockup.html` з реальними токенами, рендерить `pl design-shot docs/design/<id>/mockup.html` (скріншоти на кількох ширинах + автоматичний аудит верстки), дивиться очима й виправляє (до 3 кіл).
4. Пише `docs/design/<id>.md` за шаблоном (`pl template design`): Summary, Tokens, Screens, States, Motion, Accessibility, **Visual acceptance (V-1…V-n)**. `pl mark <id> design=done` відмовить, поки обовʼязкових розділів немає.
5. Для великого редизайну, де смак справді відкритий, питає **один раз** 2–3 напрямки (через ПМ); для дрібниць вирішує сам і виписує припущення.

### Як це доходить до розробника
- ПМ копіює **V-n як критерії приймання** (AC) у ТЗ і додає нові `data-testid`/`testID`. Тестувальник перевіряє їх на скріншотах як звичайні AC.
- Розробники (`team-frontend`, `team-mobile`) отримують шлях до `docs/design/<id>.md` і будують **точно цей вигляд**; якщо число недосяжне наявними компонентами, будують найближче й пишуть у NOTES (не «спрощують» мовчки).
- Коміт відмовляє, поки `design=yes` не став `design=done`.
- Не подобається результат: «не подобається, бо …» → ПМ кличе дизайнера з `Revise:`, а потім перебудовує розробник.
- Дизайнер не редагує код застосунку, пише лише в `docs/design/` і `.pipeline/<id>/`, і не створює артефактів (макет це HTML-файл, відкрий його у браузері).

## Частина J. Як працює тестування: тестувальник з «очима»

### Чому так
Скриптові e2e-тести довго пишуться, довго ганяються (2–3 години на поглиблене) і перевіряють лише те, що передбачив автор скрипта. Тепер тестувальник **сам дивиться**: відкриває застосунок, натискає, робить скріншот, оцінює його й вирішує, що пробувати далі, як жива людина. Скрипти пишуться лише як необов'язкова страховка (не більше одного на підтверджену помилку).

### Ліниво-розумний: не перевіряє все підряд
Тестувальник не проходить усі комбінації (мови × екрани × ролі), а **думає, що варто перевіряти**:
1. **Тріаж на початку (2 хв).** Пише `.pipeline/<id>/eyes/plan.json` і запускає `pl eyes plan`: ризик кожного AC (high/medium/low і чому), матриця класів еквівалентності з одним представником від класу (наприклад, мови: довга латиниця → `de`, кирилиця → `uk`, RTL), список того, що свідомо пропущено і чому. Без валідного плану `pl coverage` не пропустить.
2. **Ризик визначає обсяг.** Мінімум перевірок на AC: high — як у глибини (1/2/4), medium — половина, low — одна.
3. **Вибірка, а не повний перебір.** Брати можна не більше ⅓ класу. Перевірки з матриці мають поле `"class": "language/cyrillic"`, і шлюз бачить, що клас покрито.
4. **Розширення лише після падіння.** Якщо перевірка класу впала, шлюз вимагає ще принаймні один представник цього ж класу (баг в одному члені зазвичай торкається інших).
5. **Дешеві докази першими.** Текст і список елементів (`look`, `text`, `compare`) замість скріншотів; знімок відкривається лише коли треба оцінити вигляд. Нічого не перевіряється вдруге.
6. **Лічильники в кожній команді.** Остання лінія виводу: `⏱ 12.3 хв · дій 31/90 · скріншотів 9/24`. Понад м'який ліміт з'являється попередження, що тестувальник блукає.
7. **ТЗ допомагає.** Новий розділ 6b у шаблоні ТЗ («Test matrix and risk»): ПМ групує мови/екрани/ролі в класи, тоді тестувальнику не доводиться вгадувати.

### Що в нього в руках (`pl eyes`)
| | Веб | Мобільне |
|---|---|---|
| Старт | `pl eyes start web`: підіймає сервіси, відкриває браузер (Playwright), запускає годинник | `pl eyes start mobile`: підіймає симулятор, бекенди, застосунок (збірка лише коли змінився нативний код) |
| Дивитись | `look`: скріншот і список того, що на екрані (кнопки, поля, помилки) + помилки консолі й мережі | `look`: скріншот і дерево елементів |
| Діяти | `click`, `fill`, `type`, `press`, `select`, `scroll`, `back`… | `tap`, `type`, `swipe`, `scroll`, `back`, `background`, `kill`, `launch`… |
| Ламати | `net offline/slow`, `clear`, `scheme dark`, `resize` | `net offline` (Android), `backend stop`, `font large`, `scheme dark` |
| Верстка | **`sweep`**: усі ширини рівня за секунди + автоматична перевірка (горизонтальний скрол, елементи за краєм, текст поза карткою, накладання, перекриті кнопки) | — |
| Журнал | кожна дія й кожен скріншот пишуться в `.pipeline/<задача>/eyes/journal.jsonl` | те саме |

### Збіг додатка й листа (`pl mail`, `pl compare`)
Приклад: ти змінив формат листів, і вони мають виглядати так само, як у додатку.
1. Застосунок шле лист у локальний перехоплювач (Mailpit або MailHog; адреса в `workspace.json` → `"mail"`).
2. `pl mail wait` забирає лист; `pl mail shot` малює його як у пошті (десктоп 600 px і телефон 375 px), тестувальник дивиться скріншоти.
3. `pl compare` витягує з тексту додатка й листа суми, дати, час, відсотки, пошти, телефони й числа та показує: однакові, **те саме значення в іншому форматі** (`$1,234.50` проти `$1234.5`, `2026-11-05` проти `05.11.2026`), є лише з одного боку. Верстку й вигляд листа тестувальник оцінює очима.
4. У ТЗ розділ **Consistency** перелічує, що має збігатися (`K-1`, `K-2`…); без перевірки кожного пункту штамп не ставиться, а `differs` стає знахідкою з адресою, кому виправляти.

### Чому йому можна вірити
- Усі докази у звіті мають бути в журналі, створеному інструментами; вигадати скріншот неможливо.
- Є жорсткий ліміт часу за рівнем; по його завершенню інструмент не приймає дій.
- Тестувальник не бачить код і звіти розробників: працює лише за ТЗ. Якщо в Gemini/Codex (`pl run`) роль тестувальника змінила код застосунку, запуск відхиляється (`CODE_MODIFIED`).
- Розробники **не тестують** у браузері чи на симуляторі (це заборонено в їхніх інструкціях і блокується хуком), тож час не витрачається двічі.

### Що тестується
Те, що зробила задача, і детально, плюс коротко те, що могло зламатися поруч. Джерела: ТЗ (*Acceptance criteria*, *Test focus*, *Consistency*, *UI* із назвами `testID`), опис додатка (нижче), і те, що тестувальник бачить на живому екрані.

### Опис додатку для тестера — `docs/testing/<сервіс>.md`
Це найкращий спосіб пояснити тестеру твій додаток. Пишеш **один раз** простими словами (шаблон: `docs/testing/_TEMPLATE.md`):
- для чого додаток і хто ним користується (наприклад: «майстри на об'єкті, однією рукою, поганий інтернет»);
- що не має ламатися ніколи;
- типові люди і як вони поводяться;
- де найчастіше ламається;
- тестові акаунти й дані;
- що не тестувати автоматично (оплата, push…);
- пристрої та режими (маленький iPhone, темна тема…).

`/pipeline-init` запропонує заповнити його за 3–5 питаннями. Можна й руками: скопіюй шаблон у `docs/testing/mobile.md` і заповни.
Чим конкретніший опис, тим «людяніше» тестер підбирає випадки під саме твій додаток.

### Тека `e2e` / `e2e-mobile`
Потрібна лише як місце для необов'язкових регресійних тестів, які тестувальник може додати після підтвердженої помилки. Для вебу також потрібен установлений Playwright (`cd e2e && npm i -D @playwright/test && npx playwright install chromium`): це «браузер» тестувальника. Сумісність: `/test regression` ганяє всі збережені тести.

### J-resp. Перевірка верстки на різних розмірах екрана (веб)

> У новому методі це робить `pl eyes sweep` (див. вище): ті самі перевірки, ті самі набори ширин, але без написання тестів. Нижче опис того, що саме ловиться.

Веб-тестувальник тепер **завжди** перевіряє, як сторінка виглядає й поводиться на різних ширинах екрана. Для цього в `e2e/_helpers/layout-checks.ts` лежить готовий помічник (`pl scaffold` кладе його сам; у старих проєктах тестувальник створить його командою `pl template layout`).

Що перевіряється автоматично на кожній ширині:
- зʼявився горизонтальний скрол сторінки;
- елемент вилазить за край екрана;
- текст чи кнопка вилазить за межі своєї картки;
- текст обрізаний без трьох крапок, або вміст обрізаний по висоті;
- два елементи накладаються один на одного;
- кнопку, поле чи посилання перекриває інший елемент (хедер, банер, модалка);
- не завантажилась картинка.
Додатково помічник знімає скріншот на кожній ширині, а тестувальник сам дивиться перший, середній і останній, бо скрипт не бачить «негарно, але нічого не вилазить».

| Глибина | Скільки різних ширин мінімум | Які |
|---|---|---|
| поверхнево | 3 | 375, 768, 1280 |
| поглиблено | 7 | 320, 375, 414, 768, 1024, 1280, 1536 |
| дуже ретельно | 13 | від 320 до 1920 + телефон у горизонтальному режимі, низьке вікно, збільшення 200%, довгі слова й імена, великий шрифт |

Це не обіцянка агента: `pl coverage` рахує, на скількох ширинах перевірку **реально** запущено (файл `.pipeline/<задача>/layout.jsonl`), і без потрібної кількості `stamp` відмовить, а значить, не буде й коміту. Для задачі без інтерфейсу (чистий API) тестувальник пише в звіті `not_applicable.responsive` з причиною.

Перевірка в рушії Safari: `QA_WEBKIT=1 npx playwright test` (один раз `npx playwright install webkit`).

## Частина I. Один проєкт із підпроєктами (git submodules)

Мета: один «головний» репозиторій (наприклад, `fieldQuote`), а всередині нього підпроєкти `fieldQuote-web`, `fieldQuote-mobile`, `fieldQuote-backend`. У **кожного підпроєкту** своя історія, гілки і push, а весь проєкт скачується однією командою.

Для цього в git є **сабмодулі**: головний репозиторій зберігає посилання на інші репозиторії і пам'ятає, яка версія кожного з них іде в комплекті.

```
fieldQuote/                    ← головний репо (github.com/<ти>/fieldQuote)
├── .gitmodules                ← список підпроєктів і їх адрес (git створює сам)
├── .pipeline/workspace.json
├── docs/specs/  contracts/  e2e/  e2e-mobile/
├── fieldQuote-web/            ← окремий репо (github.com/<ти>/fieldQuote-web)
├── fieldQuote-mobile/         ← окремий репо (github.com/<ти>/fieldQuote-mobile)
└── fieldQuote-backend/        ← окремий репо (github.com/<ти>/fieldQuote-backend)
```

### I1. Створи репозиторії на GitHub

На github.com → **New repository**:
- `fieldQuote` — головний;
- `fieldQuote-web`, `fieldQuote-backend` — нові підпроєкти. **Постав галочку «Add a README file»**: порожній репозиторій не можна додати як сабмодуль.
- `fieldQuote-mobile` — якщо він уже є, нічого не створюй.

### I2. Збери головний проєкт

```bash
cd ~/projects
git clone https://github.com/<ти>/fieldQuote.git
cd fieldQuote

# додаємо підпроєкти: адреса репозиторію + назва папки
git submodule add https://github.com/<ти>/fieldQuote-mobile.git  fieldQuote-mobile
git submodule add https://github.com/<ти>/fieldQuote-web.git     fieldQuote-web
git submodule add https://github.com/<ти>/fieldQuote-backend.git fieldQuote-backend

git commit -m "add subprojects"
git push
```

Якщо в тебе вже є локальна папка мобільного додатку з незапушеними змінами, спершу запуш її у `fieldQuote-mobile` (`git push`), а потім додавай сабмодуль за адресою з GitHub.

### I3. Підключи кіт

```bash
cd ~/projects/fieldQuote
claude
```

```
/pipeline-init-mobile
/pipeline-init-web
```

Потім:

```bash
git add -A && git commit -m "add claude team pipeline" && git push
```

У `workspace.json` підпроєкти будуть прописані як `"path": "fieldQuote-mobile"`, `"path": "fieldQuote-web"`, `"path": "fieldQuote-backend"`.

### I4. Скачати весь проєкт (на іншому ПК чи заново)

```bash
git clone --recurse-submodules https://github.com/<ти>/fieldQuote.git
cd fieldQuote
git submodule foreach 'git checkout main'
```

⚠️ Остання команда важлива. Після клонування підпроєкти стоять не на гілці, а на конкретному коміті (стан «detached HEAD»). Ця команда перемикає кожен підпроєкт на `main`, щоб можна було нормально працювати і пушити.

### I5. Працювати з одним підпроєктом окремо

Кожна папка-підпроєкт є звичайним git-репозиторієм:

```bash
cd fieldQuote-backend
git checkout -b fix/login
# … зміни …
git add -A && git commit -m "fix: login"
git push origin fix/login          # пушиться ТІЛЬКИ бекенд
```

Головний репозиторій при цьому побачить, що бекенд змінився (`git status` у `fieldQuote` покаже `modified: fieldQuote-backend (new commits)`). Якщо хочеш зафіксувати «ця версія бекенду йде в комплекті»:

```bash
cd ~/projects/fieldQuote
git add fieldQuote-backend && git commit -m "bump backend" && git push
```

Це необов'язково робити щоразу, а лише тоді, коли хочеш зберегти узгоджений стан усього проєкту.

### I6. Через `/feature` усе робиться саме

Коли оркестратор виконує задачу, яка зачіпає кілька підпроєктів:
1. запамʼятовує поточну гілку кожного зачепленого підпроєкту й головного репо (нових гілок не створює; перед стартом переключи потрібні гілки, наприклад `staging` / `testing`);
2. агенти пишуть код у своїх підпроєктах;
3. на коміті робить **окремий коміт у кожному підпроєкті**, а потім **коміт у головному**, який оновлює посилання на нові версії підпроєктів (разом із ТЗ і тестами).

Пушиш потім одним із способів:

```bash
# все разом: спершу підпроєкти, потім головний
cd ~/projects/fieldQuote
git push --recurse-submodules=on-demand origin <твоя-гілка>

# або кожен окремо
cd fieldQuote-backend && git push origin <гілка-бекенду>
cd ../fieldQuote-web  && git push origin <гілка-веба>
```

### I7. Оновити все з GitHub

```bash
cd ~/projects/fieldQuote
git pull
git submodule update --init --recursive            # підтягнути версії, записані в головному
git submodule foreach 'git checkout main && git pull'   # або взяти найсвіжіші main кожного підпроєкту
```

### I8. Додати новий підпроєкт пізніше

```bash
cd ~/projects/fieldQuote
git submodule add https://github.com/<ти>/fieldQuote-notifications.git fieldQuote-notifications
git commit -m "add notifications service" && git push
claude      # → /pipeline-init-web (або -mobile) — допише новий сервіс у workspace.json
```

### Шпаргалка

| Хочу | Команда |
|---|---|
| Скачати все | `git clone --recurse-submodules <url>` → `git submodule foreach 'git checkout main'` |
| Запушити тільки один підпроєкт | `cd fieldQuote-web && git push` |
| Запушити все разом | у головному: `git push --recurse-submodules=on-demand` |
| Зафіксувати версії підпроєктів у головному | `git add fieldQuote-web fieldQuote-backend && git commit -m "bump"` |
| Оновити все | `git pull && git submodule update --init --recursive` |
| Подивитись стан усіх підпроєктів | `git submodule status` або `git submodule foreach git status -s` |
